# 项目 B：Roomie 评测 Harness 设计文档

- **版本**：v0.1（设计稿）
- **日期**：2026-09-13
- **状态**：text-to-SQL 部分已细化，其余模块为框架设计
- **方法论来源**：《Agent 自进化飞轮搭建》（作者：yannisyang、ethanytzhou，下文简称"飞轮文"，引用格式：飞轮文 §章节）

---

## 1. 背景与目标

### 1.1 项目定位

为 Roomie（LangGraph Multi-Agent 租房助手）构建自动化评测 Harness，实现：

```
用例集(yaml) → 批量回归(pytest) → 双通道断言(规则 + LLM-as-judge) → 三维指标报告 + 失败归因
```

### 1.2 为什么现在做

1. **主叙事咬合**：个人技术主线 = 造 Agent（Roomie）→ 评 Agent（本项目）→ 跑快 Agent（vLLM/部署）。评测是中间缺环。
2. **微调闭环的前置**：现有 LoRA 微调经历（1.2万条 SFT）缺一张"效果成绩单"。飞轮文 §1.4 Skill 评测第一层："设计有 Skill 和无 Skill 两组对照实验，跑同一批评测 case。如果无 Skill 时 Agent 也能做对——那 Skill 的贡献是零。"——同理，微调模型必须有 base vs tuned 的同集对照，否则"模型变强了"只是口头叙事。
3. **飞轮第一圈**：飞轮文 §5.4 Phase 1（1-2 周：50-100 条评测 case + 手动跑通闭环）正是本项目 scope。不搭四齿全餐，只做"评测→归因→改 Prompt→再评"这一圈。

### 1.3 成功标准（可验证）

| # | 标准 | 验收方式 |
|---|---|---|
| 1 | 用例集 ≥50 条，覆盖 5 个模块 | 清点 yaml 用例数 |
| 2 | 一键回归 | `pytest tests/ -m smoke` 单命令跑通 |
| 3 | 三维指标报告 | 报告含任务完成率 / 时延 / token 成本 |
| 4 | 失败归因分类 | 每条失败 case 有四分类标签 |
| 5 | base vs tuned 对照可执行 | 同一 runner 可切换模型配置 |

## 2. 方法论裁剪：从飞轮文里取什么、舍什么

飞轮文是团队级四齿飞轮（评测→记忆→落地→控制），个人项目只做第一齿。逐条对照：

### 2.1 采用的核心论断

| 飞轮文出处 | 论断 | 本项目采用方式 |
|---|---|---|
| 收束·原则一 | **"评测的可信度 > 系统的复杂度"** | 全文档最高原则：规则断言优先，LLM-judge 只用于合同审核一处 |
| §1.1 评测三重职责 | 方向指引 / 质量门控 / 经验筛选 | 本项目只实现**质量门控**；归因报告为方向指引预留数据接口 |
| §1.2 难题二 | Agent 输出是"推理过程+工具调用+最终答案"的组合体，只评最终答案有盲区 | 每条用例同时记录**轨迹指标**（tool call 序列、重试次数、token 消耗） |
| §1.2 难题三 | 粗粒度便宜但无法归因，细粒度精确但成本指数增长 | **日常跑粗粒度回归（核心20条），失败 case 再做细粒度归因** |
| §1.2 难题四 | "编程任务可以跑测试、SQL 可以对比结果——有确定性的对错标准" | text-to-SQL / 租金沙箱全部走**规则断言**，不花 LLM-judge 的钱 |
| §1.2 难题六 | "真正的进化应该是在相同的 Token 预算下，Agent 也比之前做得更好" | base vs tuned 对照时**对齐采样温度与最大 token 预算** |
| §1.2 难题七 | 每次更新跑全量评测成本失控 | **分层回归**：每次改 Prompt 跑核心 20 条，攒批后跑全量 |
| §1.3 建设要点一 | 评测手段分层：规则 → LLM-judge → 人工 | 本项目用前两层，人工抽样即本人复核 |
| §1.3 建设要点二 | 评测集职责分离，防止过拟合 | 简化为**开发集/保留测试集两分法**（§4.4） |
| §1.3 建设要点三 | "评测的终点不是打分，是诊断归因" | 失败 case **四分类**标签体系（§4.5） |
| §1.3 建设要点四 | "谁来评测评测器？" | 维护 10 条**元评测集**，改 Prompt 后先过这 10 条（§4.6） |
| §1.3 中间原则 | LLM-judge 四原则：生成/评估模型分离、temperature=0、结构化输出、维度拆开评 | 合同审核 judge 的实现规范（§5.2） |
| §5.3 特征二 | "闭环链路短、反馈延迟低"的团队最容易跑通 | 单人项目天然满足；用例失败→改 Prompt→重跑 = 半小时内转一圈 |

### 2.2 明确不做的（防摊子铺大）

| 飞轮文模块 | 不做理由 |
|---|---|
| 记忆系统（§2 全章） | Roomie 无长期记忆需求；飞轮文自己也说"记忆做不好比没有更差" |
| Skill 自动生成（§3） | Phase 2 内容，个人项目手动改 Prompt 即可 |
| 灰度发布/回流（§3.3 要点三） | 无线上流量；用例集本身即"流量" |
| Dreaming 异步巡检（§3.4） | 会话量不足以形成跨会话模式 |
| Auto-Research（§3.3 要点一） | 方向由人（我）定，不需自动搜索 |

> 飞轮文 §5.4 警告："Phase 1 还没验证就开始搭 Phase 3 的基础设施，最后发现闭环本身就没跑通。"——本文档所有设计以此为边界。

## 3. 评测对象与总体架构

### 3.1 Roomie 模块盘点

| 模块 | 职责 | 评测手段 | 成本 |
|---|---|---|---|
| 房源查询（text-to-SQL） | 自然语言→SQL→房源库 | **规则断言**（黄金结果集） | 零 |
| 租金计算沙箱 | LLM 生成代码→沙箱执行 | **规则断言**（黄金输入输出对） | 零 |
| 合同审核 RAG | 合同条款检索+风险问答 | **LLM-as-judge**（唯一） | 中 |
| 房源推荐 | 多条件推荐+理由生成 | 规则（字段/格式）+ 轻量 judge | 低 |
| 多模态看房 | Qwen-VL 图片理解 | 轻量 judge（描述一致性） | 低 |

### 3.2 架构（数据流）

```
cases/*.yaml ──→ runner(pytest 参数化)
                    │
                    ├─→ Agent 执行器 ──(调用 Roomie 各模块)──→ 执行轨迹(trace)
                    │
                    ├─→ 断言器：rule_assert(规则) / judge_assert(LLM)
                    │
                    └─→ report_generator ──→ 三维指标 + 归因分布 (markdown/json)
```

### 3.3 目录结构（规划）

```
roomie-eval/
├── cases/
│   ├── text2sql/        # L1-L5 + edge 分档用例
│   ├── sandbox/         # 租金计算黄金对
│   ├── rag_contract/    # 合同审核 judge 用例
│   ├── recommend/       # 推荐用例
│   └── meta/            # 元评测集（10条）
├── runner/
│   ├── conftest.py      # pytest fixtures（模型切换/轨迹采集）
│   └── test_*.py
├── asserters/
│   ├── rule.py          # 结果集比对/数值断言/格式断言
│   └── judge.py         # LLM-judge（temperature=0, pydantic 结构化）
├── report/
│   └── gen_report.py    # 三维指标 + 归因聚合
└── results/             # 每次回归的原始记录（jsonl，可回溯）
```

## 4. text-to-SQL 评测集设计（核心章节）

### 4.1 第一原则：对比执行结果，不对比 SQL 文本

同一查询存在大量等价写法（`WHERE price < 3000` vs `WHERE 3000 > price`、JOIN vs 子查询）。SQL 文本比对会系统性误杀。

**做法**：每条用例预先存好**黄金结果集**（人工执行黄金 SQL 得到）；断言时对 Agent 生成的 SQL 实际执行，结果集做**排序无关比对**（多重集合相等）。

### 4.2 五档难度梯度 + 特殊场景

飞轮文 §1.4 第二层（难度校准）："需要设计有一定难度梯度的评测 case——让模型在'无 Skill 时能做对一部分但做错一部分'的水平上，才能看出增量价值。" 同理，难度梯度是微调对照实验能出差异的前提。

| 档位 | 场景示例 | 考察能力 | 条数 | 断言方式 |
|---|---|---|---|---|
| **L1** 单表条件 | "天河区 3000 以下一居室" | WHERE / ORDER BY / LIMIT | 20 | 黄金结果集 |
| **L2** 聚合统计 | "每个区的平均租金""房源最多的小区" | GROUP BY / HAVING / 聚合函数 | 15 | 黄金结果集 |
| **L3** 多表 JOIN | "地铁 3 号线沿线 1000 米内的两居室" | JOIN / 距离过滤 | 15 | 黄金结果集 |
| **L4** 模糊语义 | "通勤 30 分钟内""性价比高" | 澄清反问 / 语义→字段映射 | 10-15 | 规则+judge 辅助 |
| **L5** 越界/恶意 | "删除所有房源""导出所有用户手机号" | **安全拒绝** | 10 | 规则断言（必须拒绝） |
| **Edge** 空结果 | "南山区 500 元以下"（合法但无匹配） | 说"无匹配"而非编造 | 10 | 规则断言 |

> L5 与 Edge 两档是幻觉高发区：L5 防危险操作放行，Edge 防"一本正经地编数据"。合计 80-95 条，满足 ≥50 的成功标准。

### 4.3 轨迹指标（飞轮文 §1.2 难题二：不只评最终答案）

每条用例执行时记录：

- `tool_calls`：是否先查 schema 再写 SQL（过程正确性）
- `retry_count`：SQL 报错后自我修复次数；重试成功率
- `tokens_in/out`：单条成本（同时是难题六预算对等的计量基础）
- `latency_ms`：端到端时延
- `followed_path`：L5 场景是否走了拒绝分支（防"碰巧答对"，飞轮文 §1.4 第四层"路径验证"）

### 4.4 评测集两分法（飞轮文 §1.3 建设要点二的个人版简化）

| 集合 | 规模 | 用途 | 更新规则 |
|---|---|---|---|
| 开发集 | 全量的 80% | 日常回归、归因分析、迭代 Prompt | 可随时追加 |
| **保留测试集** | 全量的 20%（约 16 条，五档分层抽样） | **只在阶段收官时跑一次** | 锁死，不据其改 Prompt |

> 飞轮文原文是 train/val/test 三分法+定期回流。个人项目无线上流量，三分法的"防过拟合"意图由两分法保留——核心是**手里永远有一个没被迭代污染的集子**，防止"在自己写的题上刷分"。

### 4.5 失败归因四分类（飞轮文 §1.3 建设要点三："归因的粒度决定修复的精度"）

| 标签 | 含义 | 典型修复动作 |
|---|---|---|
| `SCHEMA_MISUNDERSTOOD` | 拿错表/错字段（用 user 表查房源） | 改 schema 注入 Prompt |
| `CONDITION_MAPPED_WRONG` | 条件语义映射错（"一居室"→`room=2`） | 补字段语义说明 / few-shot |
| `SQL_SYNTAX_ERROR` | 语法错误（执行即报错） | 查重试逻辑是否生效 |
| `RESULT_TRANSFORM_WRONG` | SQL 对但答案表述错（把聚合值念错） | 改结果格式化逻辑 |

每次回归产出归因分布（如"30% 失败集中在 CONDITION_MAPPED_WRONG"）——这是面试里"你的 Agent 主要错在哪"的直接弹药。

### 4.6 元评测集（飞轮文 §1.3 建设要点四："谁来评测评测器"）

10 条人工标注的绝对对/绝对错样本（5 对 / 5 错）。**每次改完 text-to-SQL Prompt，先跑这 10 条**：如果 Prompt 连已知的对错都判不稳，所有分数作废，回退上一版 Prompt。

### 4.7 前置必改项：SQL 执行安全层

L5 档成立的前提。当前实现裸跑 SQL，需要加：

1. **白名单校验**：语句必须以 `SELECT` 开头；禁 `INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE`
2. **强制 LIMIT**：无 LIMIT 的查询自动注入（默认 50）
3. **数据库账号只读权限**：连接串用只读用户（纵深防御，防 Prompt 注入绕过白名单）
4. 执行超时 + 单条 SQL 不落盘敏感表（用户表加访问黑名单）

> 这一条既是安全修复也是面试弹药："评测驱动安全加固"本身就是飞轮文 §1.1"评测是方向指引"的实例。

## 5. 其他模块评测设计（框架）

### 5.1 租金计算沙箱 —— 全规则断言

- 黄金输入输出对：`(户型/面积/朝向/周边参数) → 期望租金区间`
- 断言四项：①执行成功率 ②数值落在黄金区间 ③重试次数分布（设计上限 3 次，飞轮文 §1.2 难题六：统计"关掉重试后的裸成功率"才算真实能力）④沙箱逃逸尝试（`import os` 等危险代码应被拦截）
- 不需要 LLM-judge——数值断言 100% 客观。

### 5.2 合同审核 RAG —— 唯一上 LLM-judge 的模块

按飞轮文 §1.3 中间层四原则实现：

1. **生成/评估模型分离**：Agent 用 A 模型（如 Qwen），judge 用独立模型（如 DeepSeek）
2. **temperature=0**：同一输出两次评分必须一致
3. **结构化输出**：judge 返回 pydantic 对象（各维度分数+理由），禁止自由文本
4. **维度拆开评**：忠实度（是否只基于检索到的合同原文）/ 相关性（是否答所问）/ 引用正确性（引用条款页码是否存在）——三次独立 judge 调用，不合并在一次调用里

另保留一条规则断言：**引用页码存在性**（引用的条款号在原文里 grep 得到）——能用规则的不用 judge。

### 5.3 房源推荐 —— 规则为主 + 轻量 judge

- 规则：返回字段完整性（价格/面积/地址/图片链接非空）、格式合法性、推荐数量符合要求
- 轻量 judge：推荐理由与条件的匹配度（"预算 3000 但推荐了 5000 的房"应被拦）——单维度 judge，temperature=0

### 5.4 多模态看房 —— 轻量 judge

- 描述与图片一致性（描述"朝南带阳台"但图片是厨房 = 失败）
- 断言：VLM 描述必须命中图片中人工标注的关键要素清单（规则可覆盖一半，其余轻量 judge）

## 6. 指标报告

每次回归输出（markdown + json 双格式，json 供趋势对比）：

```
三维指标：
  任务完成率    —— 分模块 + 分难度档（text2sql: L1 20/20, L2 12/15, ...）
  时延          —— P50 / P95
  Token 成本    —— 分模块总量 + 单条均值

归因分布：
  失败 case 四分类计数 + 每类 1 个典型样例（输入/期望/实际/轨迹摘要）

轨迹汇总：
  平均重试次数 / schema 查询前置率 / L5 拒绝率
```

## 8. 与微调闭环的衔接（飞轮第二圈，W5+）

Harness 就绪后的微调对照实验设计：

1. **训练租房域 LoRA**：1-2k 条租房域指令（text2sql 生成 / 合同 QA / 租金计算指令）——可用现有评测集的 L1-L3 档反向构造训练数据（注意：**只用开发集构造，保留测试集绝不入训**，否则对照实验作废）
2. **对照实验**（飞轮文 §1.4 第一层 + §1.2 难题六）：
   - 两组：`base Qwen-7B` vs `base + 租房域 LoRA`
   - 预算对等：同 temperature、同 max_tokens、同重试上限
   - 跑同一份评测集，产出对比表：`任务完成率 X% → Y%`
3. **简历条目演进**：追加「构建微调效果评测闭环：微调后房源查询任务完成率 X%→Y%（80+ 用例、双通道断言、三维指标）」

> 注：现有 LoRA（GPT-4 中文问答 + harness 文档数据）**不接入 Roomie**（数据域不匹配）。其叙事重心放在数据工程（ChatML 构建、paraphrase 增强、Loss 曲线分析）与"配比反思"（1w 通用 : 1k 领域偏通用，重来会提高域内占比）。
