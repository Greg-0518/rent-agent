## 2. 缺陷清单

### D1 —— 模型"凑数"：查到结果太少就放宽条件重查（**本轮最重要的发现**）

> ## ⚠ R5 更正：本节结论的**框架是错的**，改动方向也错了
>
> 见 [项目B_评测改动说明_R5.md](项目B_评测改动说明_R5.md)。
>
> 下面的**现象描述全部成立**（哪些用例、几条 SQL、分别返回几行 —— 可复核）。错的是
> 把它读成"模型凑数"：
>
> - 模型的**回答正文明确标注了**放宽部分是参考（L4-002："宠物政策**未标注**，需自行与房东确认"；
>   Edge-005：三条分标签的放宽选项 + 反问用户）。它不是假装这些行满足条件。
> - 真正的缺陷在**断言器只判最后一条 SQL**，而不是在模型的行为。
>   改成"回看所有执行过的 SQL"后，本节涉及的用例**全部转 pass，Prompt 一行没改**，
>   44/70 → 56/70。
> - 因此 §4 的**改动 1（改 `generate_query_system_prompt`）已撤回，未实施**。
> - 根因那半句（`top_k` 读起来像配额）本身没错，但实测**没造成损失**：
>   64 条 SQL 的 `LIMIT` 全部等于 `room_count` 且是模型自己写的；兜底值 `5` 从未触发；
>   推荐子图没有任何截断展示。
>
> 保留本节是为了留下证据链，**不要再照它的结论去改 Prompt**。

**覆盖 14/70 条（20%）**，且是**同一个机制**。

推荐子图是个循环 `generate_query → check_query → run_query → generate_query`，
`run_query` 把结果塞回 `messages`，模型每轮都能看到上次查了几行。
而断言取的是 `trace.sql_executed[-1]`，即**最后一条**执行的 SQL。

**症状 A：失败档 7 条里，4 条模型第一次就查出了与黄金完全一致的结果集，然后自己把它推翻了。** `[实测]`

| 编号 | 第 1 次查询结果 | 与黄金 | 最后一次查询（记分） | 结果 |
|---|---|---|---|---|
| L3-007 | `floor LIKE '%1楼%' AND (宠物 OR 养宠 OR 猫 OR 狗)` → 1 行 `(5,900,'1楼')` | **一致** | `(1楼 OR 宠物 OR …)`，AND 改 OR | 5 行 |
| L4-002 | `(宠物 OR 养宠 OR 猫 OR 狗)` → 1 行 `(5,900)` | **一致** | 条件**整个删掉**，只剩 `price<=3000` | 10 行 |
| L4-003 | `(做饭 OR 厨房 OR 可煮 OR 烹饪)` → 1 行 `(23,1380)` | **一致** | 第 2 次换近义词仍 1 行 → 第 3 次条件**整个删掉** | 10 行 |

**症状 B：存疑档 7 条，全部同一条 reason。** `[实测]`

```
Edge-001  模型先按问句查到空集（[0, 5]），又放宽条件补了 5 行作答——回答的是另一个问题，断言器判不了
Edge-003  ...（[0, 5]）...
Edge-004  ...（[0, 5]）...
Edge-005  ...（[0, 2, 5]）...
Edge-007  ...（[0, 7]）...
Edge-008  ...（[0, 5]）...
Edge-009  ...（[0, 7]）...
```

Edge 档的断言是 `count, count: 0`（`eval/cases/text2sql/edge_empty.yaml:19`）——
问的就是"确实没有"，正确答案就是"没有"。模型查到 0 行之后不甘心，放宽条件补了一批。
断言器看到"先空后满"就判 `UNVERIFIABLE`（判不了），而不是判通过或失败。

**⚠ 需要你注意**：症状 A 的 L3-010 和症状 B 是**同一件事的两个后果**——
模型查到空集/太少 → 放宽 → 结果集被写坏（判 fail）或语义漂移（判存疑）。

**根因定位** `[代码]`：[src/agent/node/recommend.py:350-362](src/agent/node/recommend.py#L350-L362)

```python
generate_query_system_prompt = """
...
除⾮⽤⼾指定了他们希望获得的特定数量的⽰例，否则始终将查询限制为最多{top_k}个结果。
..."""
system_prompt = generate_query_system_prompt.format(
    dialect=db.dialect,
    top_k=state.get("room_count", 5)      # 用户说 10 套 → 这里是 10
)
```

按我的看法，这句话有两处助推：`[推断]`

1. 它的前提是"除非用户指定了数量"——而用户恰恰指定了"推荐10套"。模型读成
   「**用户指定了 10 套，我要给 10 套**」，而不是「10 是上限」。
2. prompt 里**没有任何一句**说"匹配到几套就报几套，不要为了凑数放宽条件"。

而且 `LIMIT 10` 这个数字本身每轮都在给模型施压：它每次都能看到"配额 10、实际 1"。`[推断]`

**如果这个根因成立**，改 prompt 的预期收益：L4-002/L4-003/L4-007 三条
（第一次就已答对）很可能转 pass，Edge 档 7 条存疑很可能转 pass。
即 44 → 最多 54。**这是预测，不是结论，必须重跑才算。** `[推断]`

### D3 —— L3-001 的边界开闭（1 条）

问题：`深圳福田区楼层在30楼以上的房源，推荐10套`，`room_count=10`

```
模型 SQL   ... AND CAST(REPLACE(REPLACE(floor,'楼',''),'层','') AS UNSIGNED) > 30   ORDER BY price ASC LIMIT 10
黄金 SQL   ... AND CAST(REPLACE(floor,'楼','') AS UNSIGNED) >= 30                    ORDER BY price ASC LIMIT 10
```

福田区实际 7 套：`15楼 / 18楼 / 22楼 / 30楼 / 32楼 / 40楼 / 45楼` `[实测]`

```
>= 30  → 4 套：id 21(1950,30楼) / 30(2000,32楼) / 41(2950,40楼) / 50(3000,45楼)
>  30  → 3 套：id 30 / 41 / 50          ← 模型漏掉 id 21（30楼）
```

即"只给 3 套"不是因为它只有 3 套，也不是因为"少于 10 套"，而是**恰好有一套卡在边界上**。
`missing: [[21, 1950, '30楼']]`，`extra: []`，`limit_drift: true`。

**"少于 10 套"本身确实不扣分** —— 全量有 **23 条**用例 `pass` 时返回行数 < `room_count` `[实测]`：

```
L1-002  room_count=10  实际返回 2 行  -> pass
L1-003  room_count=10  实际返回 2 行  -> pass
L1-006  room_count=10  实际返回 6 行  -> pass
L4-012  room_count=10  实际返回 9 行  -> pass      … 共 23 条
```

边界审计（`eval/tools/audit_boundary.py`）`[实测]`：边界敏感 4 条，其中 3 条是中文区间：

```
Edge-010T  >  → >=   7 → 8    [措辞明确]
L1-011     >= → >    3 → 2    [「2500元以上」]
L3-001     >= → >    4 → 3    [「30楼以上」]
L4-012     <= → <    9 → 8    [「3000以内」]
```

三条中文用例的黄金口径**互相一致**（「以上/以内」一律含本数），所以问句没问题，
模型是真错。**但是错的类别该单独标**，见 §4 的改动 3。

### D4 —— 报告把 `missing`/`extra` 截断到 3 条，会误导读日志的人

`[代码]` [eval/asserters/rule.py:177](eval/asserters/rule.py#L177)：

```python
def _preview(counter: Counter, limit: int = 3) -> list:
    return [list(k) for k, _ in counter.most_common(limit)]
```

`detail.missing` / `detail.extra` 是给人看的**预览**，最多 3 条。真实条数只在
`reason` 文本里。二者不一致时极具迷惑性 —— **我自己就中招了**：

| 编号 | reason 里的真数 | detail 里的长度 |
|---|---|---|
| L3-007 | 缺 0 / 多 **4** | 缺 0 / 多 3 |
| L3-010 | 缺 0 / 多 **4** | 缺 0 / 多 3 |
| L4-002 | 缺 0 / 多 **9** | 缺 0 / 多 3 |
| L4-003 | 缺 1 / 多 **10** | 缺 1 / 多 3 |
| L4-006 | 缺 0 / 多 **6** | 缺 0 / 多 3 |
| L4-007 | 缺 0 / 多 **5** | 缺 0 / 多 3 |

判定本身不受影响（断言用的是完整的 `Counter`），**只是报告会骗人**。
"多 3"和"多 9"在报告里长得一模一样。

### D5 —— `top_k` 的兜底值 5 从未被覆盖（覆盖缺口）

`[实测]` 64 条执行过的 SQL，`LIMIT` **全部等于该用例的 `room_count`**，一条不差：

| room_count | 用例数 | 执行 SQL 数 | LIMIT |
|---|---:|---:|---|
| 10 | 44 | 58 | 全部 `LIMIT 10` |
| 3 | 3 | 3 | 全部 `LIMIT 3` |
| 2 | 3 | 3 | 全部 `LIMIT 2` |
| None | 20 | **0** | — |

那 20 条 `room_count=None` 的一条 SQL 都没执行（正是 L2 聚合档 10 条 + L5 拒绝档 10 条）。

所以 `state.get("room_count", 5)` 里的 **`5` 在整套 70 条里从来没生效过**。
生产环境里用户不说"要几套"时它才会生效，评测集完全没测到这条路径。
（对照 `.claude/skills/agent-eval-harness/references/suite-audit-checklist.md` 第 6 条
"这个状态测试集构造得出来吗"。）

**`LIMIT 10` 是模型自己写的，不是安全层注入的** `[代码]`：
`sql_guard._enforce_limit` 只在**没有 LIMIT** 时注入 `LIMIT 50`，
或把**超过 50** 的收紧到 50；`≤50` 原样放行。全量 64 条没有一条需要注入，
最大值就是 10，所以安全层一次都没动过——上限 50 与 `room_count` **无关**。

### 改动 2：detail 里补真实条数（约 3 行）

**为什么补**：`_preview` 截断到 3 条是**展示用**的，但它和真实条数混在同一个

### 改动 3：新增归因码 `BOUNDARY_OFF_BY_ONE`

**为什么加**：现在 7 条失败全部归到 `CONDITION_MAPPED_WRONG`，但这个筐里装了两件**修法完全不同**的事：

| 实际错法 | 修哪里 |
|---|---|
| 条件映射到错的值/列（L4-006 的 4 个近义词） | schema 说明、字段映射、Prompt 的精度要求 |
| 条件映射对了，**边界开闭错了**（L3-001 的 `>=` 写成 `>`） | Prompt 里对「以上/以下/以内」的语义约定 |

不分开的话，归因表指向的是"改 schema 说明"，而 L3-001 真正要改的是 Prompt 里的中文区间语义——
方向错了。

**判据可以机械化、误报率低**（复用 `eval/tools/audit_boundary.py` 已有的翻转机制）：

> 若 `黄金结果 ≠ 模型结果`，但 **`黄金结果翻转比较符后 == 模型结果`**，判 `BOUNDARY_OFF_BY_ONE`。

L3-001 正好命中：黄金 `>= 30` 得 4 行，翻成 `> 30` 得 3 行 = 模型的结果。

要同步改的地方：`eval/report/gen_report.py:56-66` 的 `ATTRIBUTIONS` 与
`MODEL_ATTRIBUTIONS`、`eval/tools/summary.py` 的 `ATTRIBUTION_CODES`、
`eval/conftest.py` 里的模型能力集合。

**注意**：加完这条归因后 **baseline 数字不变**（仍是 44/7/7/12），
变的只是失败那 7 条的标签分布。
